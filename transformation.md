A *presentation of an ω-order multisorted algebraic theory* (in the sense of Arkor and McDermott), or what we will call a *presentation of a lambda theory*, is given by

- a set $S$ of generating shapes
- a set $F$ of function symbols, each equipped with an input arity and an output arity.  The input arity is an expression in a language generated by starting with $S$ and closing under products and exponentials.  The output arity is an element of $S$.
- a set $E$ of equations.  Each side of an equation is a composition of function symbols and lambda terms with the same input and output arities.

A *presentation of a graph-structured lambda theory (GSLT)* is a presentation of a lambda theory with two distinguished shapes P and R and two distinguished function symbols src: R -> P and tgt: R -> P.  These src and tgt function symbols give formal sources and targets to each reduction.  A presentation then adds equations to set the formal sources and targets equal to other terms of shape P given by other function symbols, what we term the "actual" source and target.  Each formal source and target must be equated to exactly one actual source and target.

Presentations of GSLTs let us describe the operational semantics of computational calculi.  So, for example, consider the following Reflective Higher-Order asynchronous pi calculus (the RHO calculus).  Terms of shape P are "processes", terms of shape N are "names". and terms of shape R are "reductions" from the source of the reduction to the target of the reduction.  Names are serialized processes.

- shapes N (for names), P (for processes), R (for reductions)
- function symbols:
   - 0: 1 -> P, the do-nothing process constructor
   - !: N x P -> P, sending a serialized process on a name
   - ?: N x (N -> P) -> P, receiving a name on a name; the second argument is the continuation of the process that gets invoked when the name is received
   - |: P x P -> P, juxtaposition of processes
   - *: N -> P, evaluating a serialized process
   - @: P -> N, serializing a process to a name
   - src: R -> P, the source of a reduction
   - tgt: R -> P, the target of a reduction
   - comm: N x (N -> P) x P -> R, constructing a comm reduction
   - par1: P x R -> R, allowing a reduction in parallel with a process
   - par2: R x R -> R, allowing parallel reductions
   - exec: P -> R, deserializing a serialized process allows it to run
- equations
   - |(T, U) = |(U, T), | is commutative
   - |(|(T, U), V) = |(T, |(U, V)), | is associative
   - |(T, 0) = T, | is unital with respect to 0
   - src(comm(x, λy.T, U)) = |(!(x, U), ?(x, λy.T)), the source of a comm rule is a send and a receive on the same channel
   - tgt(comm(x, λy.T, U)) = (λy.T @(U)), the target of a comm rule is the evaluation of the continuation at the serialization of the sent process
   - src(par1(T, S)) = |(T, src(S)), the source of a process T in parallel with a reduction S is the juxtaposition of T with the source of S
   - tgt(par1(T, S)) = |(T, tgt(S)), the target of a process T in parallel with a reduction S is the juxtaposition of T with the target of S
   - src(par2(T, S)) = |(src(T), src(S)), the source of a reduction T in parallel with a reduction S is the juxtaposition of the corresponding sources
   - tgt(par2(T, S)) = |(tgt(T), tgt(S)), the target of a reduction T in parallel with a reduction S is the juxtaposition of the corresponding targets
   - src(exec(T)) = *(@(T)), the source of an exec is the deserialization of the serialization of T
   - tgt(exec(T)) = T, the target of an exec is T itself

I am interested in a transformation of presentations of GSLTs that transforms an untyped calculus into a typed one in a similar way to how the calculus used in Barendregt's lambda cube extends the untyped calculus with extra function symbols, after which he defines typing as a relation between terms.

The transformed presentation of the calculus follows:

- shapes N (for names), P (for processes), R (for rewrites)
- function symbols
   - 0: 1 -> P, the do-nothing process.
   - 00: 1 -> P, the type of the do-nothing process.
   - !: N x P -> P, a send process.  The first parameter is the name to send on and the process to send.
   - !!: N x P x N -> P, the type of a send.  The first two parameters are the type of the name to send on and the type of the sent process.  The third input, the name itself to send on, is necessary because the comm reduction requires a match between the name used for sending and receiving.
   - ?: N x (N -> P) -> P, a receive process.  The first parameter is the name being listened to, and the second parameter is the continuation.
   - ??: N x N x (N -> P) x N -> P, the type of a receive. The first parameter is the type of the name being listened to, the second parameter is the type of the name being fed to the continuation, the third parameter is the dependent type of the continuation, and the fourth parameter is the name being listened to itself.  The fourth parameter is necessary because the comm rule requires a match between the name in the send and the name in the receive.
   - |: P x P -> P, a juxtaposition of processes.
   - ||: P x P -> P, the type of a juxtaposition. The parameters are the types of the processes being juxtaposed.
   - *: N -> P, a process that's a deserialized name.  The input is the name to deserialize.
   - **: N -> P, the type of a process that's a deserialized name.  The input is the type of the name being deserialized.
   - @: P -> N, a name that's a deserialized process.  The input is the process to serialize.
   - @@: P -> N, the type of a name that's serialized process.  The input is the type of the process being serialized.
   - src: R -> P, the formal source of a reduction.  The input is the reduction.
   - srcsrc: R -> P, the type of the formal source of a reduction. The input is the type of the reduction.
   - tgt: R -> P, the formal target of a reduction.  The input is the reduction.
   - tgttgt: R -> P, the type of the formal target of a reduction. The input is the type of the reduction.
   - comm: N x (N -> P) x P -> R, a comm reduction. The first input is the name the send and receive processes are synchronizing on. The second input is the continuation of the receive process, and the third input is the process being sent.
   - commcomm: N x N x (N -> P) x N -> R, the type of a comm reduction. The first parameter is the type of the name on which the send and receive are synchronizing.  The second parameter is the type or kind of the name the continuation will receive.  The third parameter is the dependent type or kind of the continuation. The fourth parameter is the name itself on which the send and receive are synchronizing.
   - par1: P x R -> R, allowing a reduction in parallel with a process. The first input is the process and the second input is the reduction.
   - par1par1: P x R -> R, the type of a par1 reduction. The first input is the type of the process and the second input is the type of the reduction.
   - par2: R x R -> R, allowing parallel reductions.  Both inputs are reductions.
   - par2par2: R x R -> R, the type of a par2 reduction.  Both inputs are the types of the reductions.
   - exec: P -> R, deserializing a serialized process allows it to run.
   - execexec: P -> R, the type of the process that gets serialized and then deserialized.
   - ctxrecv_i: N x N x (N -> P) x N x P -> P, the independent possibility modal type of a process in the context of a receiving process.  ctxrecv_i(T, U, V, W, X) is the type of a process that when juxtaposed with a process of type ??(T, U, V, W) possibly reduces to a process of type X.
   - ctxrecv_d: N x N x (N -> P) x N x P x P -> P, the dependent possibility modal type of a process in the context of a receiving process.  ctxrecv(T, U, V, W, X, Y) is the type of a process that when juxtaposed with a process of type ??(T, U, V, W) possibly reduces to a process Y of type X.
   - ctxcomm_i: N x N x (N -> P) x N x P -> P, the independent possibility modal type of a process in the context of being sent to a receiving process.  ctxcomm_i(T, U, V, W, X) is the type of a process that when sent on a channel W and juxtaposed with a process of type ??(T, U, V, W) possibly reduces to a process of type X.
   - ctxcomm_d: N x N x (N -> P) x N x P x P -> P, the dependent possibility modal type of a process in the context of being sent to a receiving process.  ctxcomm_d(T, U, V, W, X, Y) is the type of a process that when sent on a channel W and juxtaposed with a process of type ??(T, U, V, W) possibly reduces to a process Y of type X.
   - ctxsend_i: N x P x N x P -> P, the independent possibility modal type of a process in the context of a sending process.  ctxsend_i(T, U, V, W) is the type of a process that when juxtaposed with a process of type !!(T, U, V) possibly reduces to a process of type W.
   - ctxsend_d: N x P x N x P x P -> P, the dependent possibility modal type of a process in the context of a sending process.  ctxsend_d(T, U, V, W, X) is the type of a process that when juxtaposed with a process of type !!(T, U, V) possibly reduces to a process X of type W.
   - ctxposs_i: P -> P, the general independent possibility modal type.  ctxposs_i(T) is the type of a process that possibly reduces to a process of type T.
   - ctxposs_d: P x P -> P, the general dependent possibility modal type.  ctxposs_d(T, U) is the type of a process that possibly reduces to a process T of type U.
- equations
   - |(T, U) = |(U, T), | is commutative
   - ||(T, U) = ||(U, T), || is commutative
   - |(|(T, U), V) = |(T, |(U, V)), | is associative
   - ||(||(T, U), V) = ||(T, ||(U, V)), || is associative
   - |(T, 0) = T, | is unital with respect to 0
   - ||(T, 00) = T, || is unital with respect to 00
   - src(comm(x, λy.T, U)) = |(!(x, U), ?(x, λy.T)), the source of a comm rule is the juxtaposition of a send and a receive on the same channel
   - (assuming y fresh with respect to V) srcsrc(commcomm(T, U, λy.V, x)) = ||(!!(T, **(U), x), ??(T, U, λy.V, x)), the type of the source of the comm rule is the type of a juxtaposition of the type of a send and the type of a receive on the same channel.
   - tgt(comm(x, λy.T, U)) = (λy.T @(U)), the target of a comm rule is the evaluation of the continuation at the serialization of the sent process
   - (assuming y fresh with respect to V) tgttgt(commcomm(T, U, λy.V, x)) = V, the type of the target of the comm rule is the type of the body of the continuation.
   - src(par1(T, S)) = |(T, src(S)), the source of a process T in parallel with a reduction S is the juxtaposition of T with the source of S
   - srcsrc(par1par1(T, S)) = ||(T, srcsrc(S)), the type-level lifting of the previous rule
   - tgt(par1(T, S)) = |(T, tgt(S)), the target of a process T in parallel with a reduction S is the juxtaposition of T with the target of S
   - tgttgt(par1par1(T, S)) = ||(T, tgttgt(S)), the type-level lifting of the previous rule
   - src(par2(T, S)) = |(src(T), src(S)), the source of a reduction T in parallel with a reduction S is the juxtaposition of the corresponding sources
   - srcsrc(par2par2(T, S)) = ||(srcsrc(T), srcsrc(S)), the type-level lifting of the previous rule
   - tgt(par2(T, S)) = |(tgt(T), tgt(S)), the target of a reduction T in parallel with a reduction S is the juxtaposition of the corresponding targets
   - tgttgt(par2par2(T, S)) = ||(tgttgt(T), tgttgt(S)), the type-level lifting of the previous rule
   - src(exec(T)) = *(@(T)), the source of an exec is the deserialization of the serialization of T
   - srcsrc(execexec(T)) = **(@@(T)), the type-level lifting of the previous rule
   - tgt(exec(T)) = T, the target of an exec is T itself
   - tgttgt(execexec(T)) = T, the type-level lifting of the previous rule
   - ||(ctxrecv_i(T, U, V, W, X), ??(T, U, V, W)) = ctxposs_i(X)
   - ||(ctxrecv_d(T, U, V, W, X, Y), ??(T, U, V, W)) = ctxposs_d(Y, X)
   - ||(!!(T, ctxcomm_i(T, U, V, W, X), W), ??(T, U, V, W)) = ctxposs_i(X)
   - ||(!!(T, ctxcomm_d(T, U, V, W, X, Y), W), ??(T, U, V, W)) = ctxposs_d(Y, X)
   - ||(ctxsend_i(T, U, V, W), !!(T, U, V)) = ctxposs_i(W)
   - ||(ctxsend_d(T, U, V, W, X), !!(T, U, V)) = ctxposs_d(X, W)

I sort of intuited this transformed grammar, but I would like to have formal rules for doing the transformation.  Here are rules for producing the new set of function symbols:

For each function symbol f:∏_i A_i -> B in F, we get an additional "type-lifted" function symbol f':∏_i T(A_i) -> T(B) in F':

- When A is a generating shape G, T(A) = G.
   - For example, *: N -> P, so 
    
        **: T(N) -> T(P) = **: N -> P.

- When A is a product of shapes A₁ x A₂, T(A) = T(A₁) x T(A₂).
   - For example, |: P x P -> P, so 
    
        ||: T(P x P) -> T(P) = T(P) x T(P) -> T(P)
                             = P x P -> P.

- When A is an arrow of shapes A₁ -> A₂, T(A) = T(A₁) x T(A₁) -> T(A₂).
   - For example, ?: N x (N -> P) -> P, so
    
        ??: T(N x (N -> P)) -> T(P) = T(N) x T(N -> P) -> P 
                                    = N x T(N) x (T(N) -> T(P)) -> P
                                    = N x N x (N -> P) -> P

Let a *base reduction* be a function symbol whose input arity does not use R and whose output arity is R.  For each base reduction B: ∏ᵢ Aᵢ -> R, consider the actual source of B, C = src ⚬ B: ∏ᵢ Aᵢ -> P.

- Suppose that some input aⱼ: Aⱼ is duplicated and appears as an input to a function symbol D in C.  Then we extend the input to the type-lifted function symbol DD by Aⱼ.
   - For example, in comm: N x (N -> P) x P -> R, src(comm(T, U, V)) = |(!(T, V), ?(T, U)). Without this rule we'd have
    
        !!: T(N x P) -> T(P) = T(N) x T(P) -> T(P)
                             = N x P -> P
        ??: N x N x (N -> P) -> P  by calculation above
    
     but T is duplicated in `|(!(T, V), ?(T, U))`, appearing as an input to `!` and `?`.  So we get an extra "x N" in the type lifted function symbols `!!` and `??`:
    
        !!: N x P x N -> P
        ??: N x N x (N -> P) x N -> P

     Or equivalently,
    
        !!: N x P -> (N -> P)
        ??: N x N x (N -> P) -> (N -> P)

     so we can reuse the equations from the non-type-lifted function symbols (see below).

- The abstract syntax tree for C has internal nodes labeled by function symbols and leaves labeled by shapes.  For each occurrence of P as an input to a function symbol in the AST, we get two possibility modal types expressing the fact that the process-shaped subtree of the AST in the context surrounding that subtree possibly reduces to the target of the base reduction.  One of the possibility modal types is "independent", and only has type information; the other is "dependent", and tracks the specific target process as well.
   - For example, src(comm(T, U, V)) = |(!(T, V), ?(T, U)).  There are three process-shaped proper subtrees of |(!(T, V), ?(T, U)):
     
     1. V in the context |(!(T, []), ?(T, U)), giving rise to the modal types ctxcomm_i and ctxcomm_d
     2. !(T, V) in the context |([], ?(T, U)), giving rise to the modal types ctxrecv_i and ctxrecv_d
     3. ?(T, U) in the context |(!(T, V), []), giving rise to the modal types ctxsend_i and ctxsend_d
     
     I chose names for the modal type function symbols based on my knowledge of the semantics of the comm rule, but a formal transformation should choose names based on the location of the subtree instead.


Finally, we add the function symbols ctxposs_i: P -> P and ctxposs_d: P x P -> P.
